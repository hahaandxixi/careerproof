## 目标与实施次序

1. 先为核验链建立每次物理HTTP尝试的持久身份和状态，可信响应恢复入账；不以任务状态、内存序号或业务结果代替用量事实。
2. 再覆盖主匹配链所有规划/分析/修正/HTTP重试；切换聚合账本须避免同一消费同时计逐次与聚合。
3. 两链共用日预算预留在下一张卡落地；本卡设计必须留下发送日、输入/输出上界和未结清状态，不声称已解决并发超额。
4. career_planning/visual_evidence/job_drafting另列后续范围；未经核对不声称全系统已统一。

## 必须保持的协议

| 事实 | 判定与边界 |
| --- | --- |
| attempt身份 | 每个实际HTTP尝试独立attempt_id，关联task/run_token/step及物理重试号；编号在发送前生成，不能复用成功响应计数 |
| not_sent | 已建立持久记录但未提交发送意图，可按CAS终止；不得根据租约过期直接推断未发送 |
| in_flight | 发送意图短事务已提交，HTTP在事务外；硬停后表示可能发送，不能承诺确切发送事实 |
| received_unbooked | 已持久化可信usage原值、响应标识或安全摘要及接收时间；原始业务内容不进入日志，无效/缺失usage不是零消费 |
| booked | attempt唯一账目与结清状态同事务提交；重复恢复不重发HTTP、不重复消费；旧run仍可入账但不能恢复结果 |
| usage_unknown | 超时或未持久收据保留未知及原因；没有权威收据不能精确恢复token；不得TTL直接消除可能消费 |

取消/撤回/租约失效不能回滚已消费账目，也不能让恢复入账重新展示旧结论。发送前与终结时分别短事务核查投递授权/固定快照，不能持授权行锁等待HTTP。已有run_token+request_seq历史唯一约束及旧账目不得丢失。新旧记账路径明确切换标记，以防重复计费。对账恢复只处理数据库事实，不重发原请求。

预算协议预留：锁序为用户日容量行→稳定attempt行→ledger；多日按日期升序。归属日以Asia/Shanghai发送意图提交日固化，跨午夜须重新准入。预留与实际消费不同；未知占额调整必须有原因、操作者和审计记录。人工额度政策仅结清预留，不伪造provider实际消费。
