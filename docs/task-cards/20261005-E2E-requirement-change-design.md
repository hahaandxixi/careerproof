# E2E-03：岗位要求变化的产品协议待补

Codex设计准备，2026-10-05。依据student-preflight的实际代码调查：已有报告岗位锁定要求，growth分析固定原jobId，比较服务拒绝不同jobId。因此目标所要求的“只换岗位要求/材料与要求同时改变”尚未实现真实页面链路。不能把锁定返回409、离线comparison测试或手工插入两份报告当成目标完成。

## 本次拟定方向（实现前需独立审查）

1. 保留已有报告岗位锁定、原报告和企业投递快照；要求调整走新建岗位，不原地改历史数据。
2. 学生明确选择新的可见岗位，才允许在私人补证分析中改变目标岗位；默认仍用原岗位。两份报告必须都是同一学生有权读取的报告。
3. 材料相同且目标岗位相同仍拒绝重复补证；材料相同而目标岗位确已改变，可以生成要求变化对照。上传的新材料与新岗位同时选择时，两个背景标签分别展示。
4. 不按技能名偷偷合并不同岗位的requirementId。不同要求身份展示原要求移除/新要求新增；显式展示原/目标岗位和要求快照、材料版本、规则/模式变化。不得把分数变化归因为本人能力提升。
5. 新岗位许可复用真实分析服务的可见性/状态校验；分析队列、材料固定、重复点击幂等、跨用户/失效目标拒绝必须有回归。分析开始后目标不得被换掉。
6. 明确比较只在此主动选择的流程开启；原默认同岗位比较保持原语义。任务原问题/引用/企业回复关联仍指向固定基准要求，不把新要求伪装成原企业问题。
7. 不加入真实模型调用或自动再次投递；新版报告私有，原企业A/B/A2快照字节不变。

## 尚需代码设计核对

目标jobId如何持久固定与重读（AnalysisTask已有jobId是否充分）；材料相同的选择如何不让原同岗位空补证通关；comparison调用的显式跨岗位许可；前端岗位选择和任务原/目标背景展示；新岗位发布/撤销/分析途中状态变化。

未经上述协议和测试核对，不委派直接改数据库结构或放宽全局compare_views约束。下一步先完成已有同岗位学生闭环并独立审查本协议，然后实现两种要求变化路径、页面复测和固定快照签收。本卡不是用户批准请求，不改变原目标完成标准。

## 已收敛的实现合同（2026-10-05）

- Codex独占后端schema/model/migration/service/comparison及相关回归。新增nullable `EvidenceGrowthTask.target_job_id`，旧任务NULL代表原岗位；`GrowthMaterials.targetJobId`可省略（原岗位）。attach验证公开published岗位及本人材料，在一个短事务中保存目标和版本。相同材料只有明确不同目标岗位才允许。
- analyze不接受临时目标覆盖，使用已保存目标；沿用create_match_task的发布状态/要求/用户/并发校验。已有非失败分析锁定两种选择；失败后人工重新保存才可重试，不自动换目标或重发。
- GrowthTask响应新增`targetJobId`/`targetJobTitle`（有效已保存目标，旧任务为原岗位）。ReportComparison新增base/target JobId/Title及`contextChanges: job`；跨岗位许可仅用于已配置新目标的growth，不放宽默认报告比较。同一candidate校验始终保留；不同requirementId分别新增/移除，不映射为同一能力。
- 免费ZCode前端仅拥有domain.ts/client.ts、GrowthWorkspace/GrowthComparison、growth-workflow标签及自己的新增回归和新证据。公开岗位选择和已保存原/目标展示；保存POST带targetJobId；未保存变化不能误示为已保存，分析按钮使用固定选择；无自动同意AI/投递，不调用真实模型。不得操作数据库/迁移/构建/浏览器/重启。
- 新migration仅增加可空目标字段/FK，不修改原任务快照、原报告或投递。先隔离SQLite/PG迁移回归；E2E数据库实际迁移/重启须等企业任务交棒。当前backend全量旧基线未终态前不改后端源文件，以免证据混合。
