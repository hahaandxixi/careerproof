# OPS-01A：硬停对账与在途预算只读调查卡

2026-10-05。Codex排序准备，尚未下发。PRODUCT-01仍先验收；本卡不授权修改账本协议、迁移数据库或调用真实模型。

## 问题与依据

- 当前核验响应的可信非负整数用量按run_token+request_seq独立幂等入账，取消/撤回/租约失效不应回滚已入账事实。已完成B-08范围保持。
- application_verification.py的persist_verification_usage从provider.usage_records内存读取；provider.py在响应处理后追加记录。进程在捕获/提交前硬停，内存记录可能消失，不能从task失败推断未消费，也不能用估算伪造实际账目。
- 核验预算检查在外部请求前释放用户行锁；analysis._daily_ai_budget只汇总已落AiUsageLog，在途调用未预留，多个获准请求可能共同超限。必须调查报告主链与企业核验两种调用，不能只修一条后声称系统预算一致。

Codex：审查未知状态和授权边界，定账本/预留协议、迁移与锁序、独立故障验证；协议签收后才授权有界实现。当前PRODUCT写入者不被本任务打断。

## 必须交付的问题

1. 两条链每个请求的持久标识、实际外发时机、模型重试次数、捕获时机和独立入账路径；区分客户端重试与同一次响应重复入账。
2. 提议的状态机至少区分未发送、在途、已收到可信用量待入账、已入账、用量未知；列出每次状态转移的持久事实与原子事务边界。预留不是实际消费，不能把usageKnown当usageBooked。
3. 硬停发生在发送后但响应未持久化时，哪些事实能够恢复、哪些必须保持unknown；没有可信提供商收据/查询就不能承诺精确恢复token。本轮不访问提供商账户或外部对账API。
4. 日输入/输出与请求数限额如何同时涵盖实际已账+在途保守预留；明确锁序、跨日、超时、租约重领和旧run延迟响应。不能仅以TTL过期就释放可能仍消费的调用额度。
5. 可恢复预留/账目处理必须幂等；重试对账不重新发送原请求，不复活撤回结论，保留固定投递快照和取消后隐私边界。
6. 三种故障证据设计：真实子进程硬停（仅自有PID/开始时间匹配且mock提供商）、数据库暂时失败后恢复、PG并发预算争夺。所有数据限专属cp_test/临时SQLite；不复用closure投递。
7. 依赖调查仅读取锁文件/已安装版本，现有漏洞表视为历史线索；本任务不自行更新版本或把旧漏洞数字冒充当前审计。外部漏洞查询另定范围。
