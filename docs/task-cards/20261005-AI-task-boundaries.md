## 结果与设计约束

1. 第三方/参考或小组产物不得直接作为个人实践、能力、负责范围的证明。拒绝肯定的替代归属；保留“不能作为”“尚待核对”“对照参考后补个人记录”等明确保留边界的有效计划。不把未来提交“本人贡献证明”这一交付物名称当作已证实贡献。
2. 已展示来源对同一具名功能作相反实现状态声明时，计划必须并列出处、核对版本/时间并保留待核验结论，不静默选边。仅实现窄而明确的同一主语“已实现/尚未实现”一致性检查；不宣称能判断任意自然语言矛盾。不同版本或已明确解释的演进不得误当冲突。
3. 计划若预设“完整功能/完整链路”直接验收，先要求核对现有实现范围、缺失分支或补全实现，再进入验收；这是一条补证流程边界，不是静态程序完整性判定。只收集完整运行记录、验证现有具名函数等正常计划不应被误拒，不能要求重复上传已展示源码。
4. 原拒绝/修复重试/规则降级路径保留。契约失败必须进入可解释降级，不把无效计划存入可采纳任务；失败输出不泄露真实材料。不得为了四个例子变绿修改其预期拒绝，新增变体、否定/待核验正例和合法未来计划以防过拟合。
