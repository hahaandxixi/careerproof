
原句「`片段可见 FastAPI 应用实例和 /health 路由，函数返回 {"status": "ok"}…当前引用已覆盖该函数原文及整文件。`」
与输入一致：R1-E1 恰为装饰器+函数+返回（4–6 行），R1-E2 为整文件（1–6 行），覆盖描述属实。

**② 空实现/矛盾：无需识别。** 材料无空实现、与简历声明（"使用 FastAPI 编写健康检查"）不矛盾。
原句「`属于与健康检查直接相关的非空处理逻辑`」准确——`return {"status": "ok"}` 确为非空返回。

**③ 夸大检查：无。**

未声称已运行、未声称本人贡献、未把静态代码说成"能力通过"。

**④ 建议可执行性：可执行。** 交付物、步骤、验收点都具体：

2. 建议索取运行记录，超出"提供实现材料"的字面要求；作为核验手段合理，但可注明"可选、非本要求必需"。

## 样本 M03 `contradictory-return` —— **1 处确定缺陷（内部自相矛盾）**

**输入片段**（`maths.py`，R1-E1=第1–2行）

```text
1 def sum_positive(values):
2     return 0
```

**① 引用支持结论：部分支持（结论对，判据自相矛盾）。**
结论层原句「`函数体固定返回 0，未展示筛选正数或求和逻辑，与简历自述矛盾。`」——与输入一致。
但 `rating.criteria[0]`（relevance）自相矛盾：

- 同一条判据中：`supported: false`，而 reason 写「`函数名与要求相关，但函数体未展示筛选正数或求和内容。`」
  ——理由前半句**承认函数名与要求相关**，却将其判为"不支持"。
- 与 M02 同类结构口径不一致：M02 同样是空实现，但 relevance 判 `supported: true`
  （理由「`片段包含 FastAPI 应用与 /tasks 路由定义，与要求直接相关。`」）；M03 的 `sum_positive(values)`
  与"筛选正数并求和"的直接相关程度不低于 M02 的路由装饰器，却判 false。

**后果**：`rating.level` 由 M02 的 `1` 降为 `null`，`reason` 也随之写「`三项判据均无证据支持`」——
与"函数签名确实直接对应要求"的事实不符。方向上属**低估**（不是夸大），但语义不一致会让展示与统计口径漂移。

**最小修改方向（仅供人工/维护者参考，本卡未改任何代码或提示词）**：把 relevance 判为 `true` 并保留 level 1；
或改写 reason 去掉"函数名与要求相关"的表述以自洽。两种都能消除矛盾，前者更贴近"M02 同口径"。

**② 空实现与矛盾：识别正确。** 原句「`函数体只有 return 0，未展示筛选正数或累加求和；简历声称已实现筛选正数并求和，与可见实现不一致。`」

**③ 夸大检查：无。** 原句「`未提供运行结果或本人贡献记录`」；未声称实现成功。

**④ 建议可执行性：可执行。** 原句「`提交含筛选正数与求和逻辑的新版本 maths.py，提供该版本的运行输出或测试记录`」；
验收点「`运行记录显示对含负数输入的期望输出`」具体可核。
