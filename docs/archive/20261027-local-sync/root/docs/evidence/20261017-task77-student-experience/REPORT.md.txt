## 二、连接提示：五种情形与实际结论

原逻辑（本轮之前就存在，未改）：`connection` 状态机 `connecting → live ↔ polling → idle`，
以及 `onerror`/解析失败/请求失败时 `schedulePoll()`、终态时 `stopStream()+idle`。

| 情形 | 触发点 | 状态变化 | 显示文案 |
| --- | --- | --- | --- |
| 首次连接 | effect 起始 | `connecting` | 正在连接实时进度 |
| 连接建立 | `EventSource.onopen` | `live` | 实时更新中 |
| `onerror` | `source.onerror` → `stopStream()`+`schedulePoll()` | `polling` | 实时连接已中断，正在定时刷新 |
| 解析失败 | `applyEvent` JSON 解析异常 → `stopStream()`+`schedulePoll()` | `polling` | 同上（流已被主动关闭，与 onerror 同一转移） |
| 重连成功 | 轮询后 `loadTask` → `openStream()` → 新流 `onopen` | `live` | **实时更新中**（不残留"中断"） |
| 任务终态 | SSE 终态负载或 API 返回终态 | `idle` | 任务已结束，状态不再变化 |

**本轮新增（纯展示，不改转移）**：
- `streamSupported`：区分"环境无 EventSource"与"流被断开"；
- `streamOpened`：记录是否曾真正 `onopen` 过，避免首次连接失败就说"已中断"；
对应文案新增一档"实时进度暂未建立，正在定时刷新"。

**核对结论**：
1. **重连成功不会继续显示中断**——`onopen` 必置 `live`，文案随之为"实时更新中"。
2. **连接异常不改变业务终态**——`connection` 只由流/请求信号驱动；`task.status` 只由 SSE 负载或
   `GET /analysis-tasks/{id}` 写入，二者无交叉写入。断线后仅切到轮询，不标失败、不推进进度。
3. 说明一处原逻辑特性（非本轮引入、未改）：`loadTask` 内判断 `connection === "polling"` 时闭包捕获的是
   effect 建立时的值，因此轮询后仍会尝试 `openStream()`，这实际构成重连；本轮未动它，仅记录。
