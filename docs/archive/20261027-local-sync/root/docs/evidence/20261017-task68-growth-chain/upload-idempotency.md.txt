## 新增最小回归（本轮唯一源码改动）

`backend/app/tests/test_portfolio_api.py:295-379`
`test_upload_request_key_is_scoped_to_owner_and_project`

复用该文件既有的**独占临时 SQLite** fixture（`tmp_path`，仅建本测试所需表），走真实 HTTP 路由、真实 service/repository，不连接正常数据库。断言：

1. Bob 用 Alice 的 `requestId` 直接 POST 到 Alice 的项目 → **404**；Alice 项目仍只有 1 个 `alice.zip` 版本，版本 id 不变。
2. Bob 在自己新建的项目复用同一 `requestId` → 202，得到**自己的新 versionId/taskId**（均与 Alice 不同），历史里只有 `bob.zip`，没有取得 Alice 的结果。
3. Alice 把同一 `requestId` 用于**另一个自己的项目**且内容不同 → 202，在新项目生成 `second.zip` 新版本；原项目仍是 `alice.zip`，未把旧材料静默挂到新项目。
4. 回到原项目，用原 `requestId` + 原字节重放 → 202，`projectId/versionId/taskId` 与首次完全一致。

说明：第 3 条符合**现有契约**（键按目标项目唯一），但不是全局 owner 级幂等；若协议希望跨项目复用同键也拒绝，属于协议决策，见“剩余问题”。

## 未验证 / 剩余问题

- **并发同键未验证**：临时 SQLite 不验证 PostgreSQL 行锁；未分配专属 PG，未做并发请求。顺序重试验证 ≠ 并发幂等验证。生产路径依赖 `SELECT ... FOR UPDATE` 串行化，建议有 PG 时补一条并发同键测试（参考现有 `test_visual_postgres_concurrency.py` 的夹具方式）。
- **未跑真实网络/浏览器**：测试为 ASGITransport + 隔离 SQLite，不是独立服务或页面证据。
- **跨项目复用同键**：当前生成新版本而不拒绝。符合现有 `(project_id, request_id)` 约束，也不会串材料；但若产品协议要求“一个 owner 内 requestId 全局唯一”，需协议层确认，最小改法是增加 owner 级幂等记录/唯一键并在目标不匹配时拒绝，而不是只靠项目内唯一约束。
- `create_project_version` 与 `create_project` 不同，未捕获插入时的 `IntegrityError`；在项目行锁下预期不会触发，但 PG 并发测试可确认是否需要在唯一键冲突时回放/返回 409。
