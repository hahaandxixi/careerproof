## 发现（按可行动优先级；区分已复现/设计建议）

**[发现1 · 合同漏洞，代码路径完整可达（未执行，需DB）] 通用 retry 端点绕过"失败后人工重存"门**
`POST /analysis-tasks/{task_id}/retry`（api/v1/analysis.py:87-100）→ `retry_match`（analysis.py:288-294，job_match 且所有权通过）→ `reset_failed_task`（task_lifecycle.py:130-155，owner-only CAS FAILED→PENDING）。growth 行引用的失败分析可被学生经通用端点直接重置重跑，不经 growth attach——与 409 文案"请重新核对并保存材料后再发起"及合同"失败后人工重新保存才可重试"冲突；view 侧（L250）会照常接受该任务（jobId 一致）并最终可比对。收敛二选一：retry_match 检测 `EvidenceGrowthTask.analysis_task_id` 引用并拒绝（引导 attach），或合同明文将"通用重试"定义为合规人工重试。必配回归：失败后直接 retry → 按现合同期望 409。

**[发现2 · 探针已复现的不一致，需产品裁决] 两处 material_key 定义不同**
attach 键 `(kind, contentHash, materialRole)` 忽略版本 id（evidence_growth.py:26-28，注释明言同内容新版本≠材料变化）；compare 键 `(kind, id, contentHash)` 计版本 id（report_comparison.py:85-87）。探针 P3e：同内容新版本跨岗位对照的 contextChanges 含 "materials"，而 attach 语义认定材料未变。展示层会同时出现"材料未变（attach 放行原因）"与"材料版本变化（context）"。合同要求显式展示"材料版本"——compare 现行为可辩护，但建议统一口径或对仅 id 不同、hash 相同的情形加注。

**[发现3 · 设计建议] limitations[3] 位置耦合**：growth.view 按索引覆写 `comparison.limitations[3]`（evidence_growth.py:273-275）。今天 [3] 恰是复核状态行（探针 P4），跨岗位流程日后在 compare_views 增删 limitation 会静默覆写错行。建议按内容前缀匹配替换。

**[发现4 · 设计建议] attach 不预检目标岗位要求**：attach 只验 published（L169-173）；"岗位尚未设置能力要求"仅在 analyze 时由 create_match_task 拒（analysis.py:203-204）→ 空要求岗位晚失败进 FAILED/人工重存。可并入 attach 或作为既定路径加测试。

**[发现5 · 设计建议/测试点] 去重与缓存绑定**：create_match_task 对同输入 pending/running 幂等返回（analysis.py:205-218）、同 cacheKey 完成任务返回缓存（L255-272）——growth.analyze 可能绑定早于 growth 任务创建的既有报告（jobId/materials 校验均过）。合同未禁止；建议测试固化，且前端不得把复用报告宣称为本次生成。

**[发现6 · 测试点] SQLite 外键强制**：迁移回归与"岗位删除→标题回退"路径（L223-225）在 SQLite 需 `PRAGMA foreign_keys=ON` 才有意义（FK RESTRICT 在 model L22-24 / 迁移 0014）。

**[发现7 · 合同留白] 单行约束**：`(created_by, base_report_id, requirement_id)` 唯一（model L12）保留——同一基准要求仅一个 growth 行；已 compared（锁定）后换新目标只能"从新报告创建后续任务"链式推进（要求身份随之指向新报告，原企业问题关联按合同留在原任务）。建议合同明文此限制并补链式回归。

**[发现8 · 观察项] 防漂移 409 的列表副作用**：view 的 input_snapshot.jobId 不一致 409（L250-251）会让 list 静默跳过该行（L142-152 仅 warning 日志）——防御检查失败模式是任务从学生列表消失。建议 list 层降级标记或更醒目告警。

## 必要测试清单（最小集）

1. attach：同材料+无 target→409；同材料+target=原岗位→409；同材料+不同 target→持久化成功且 targetJobId 回读正确；非 published 目标→404 与 create_match_task 同谓词（测试钉住同源）。
2. 锁：analyzing 中改材料或改 target 均 409；analyze 幂等重复点击返回同视图；行锁串行化并发 attach/analyze。
3. 失败链：analyze 失败→再 analyze 409→attach 重存（同新版本材料可）→新 AnalysisTask；**通用 retry 对 growth 失败任务→期望 409（发现1）**。
4. 状态变化：attach 后目标 unpublish→analyze 失败→人工重存；运行中 unpublish→报告仍生成、比较可用（合同未定义，需先定语义）。
5. 比较：探针 P1/P2/P3/P3b 固化为回归（默认拒、candidate 恒拒、按 requirementId 增移、contextChanges=job）；旧任务响应 targetJobId=原岗位；input_snapshot.jobId 漂移→409。
6. 迁移：SQLite(+PRAGMA)+PG 上 0014 只加可空列+FK，旧行三 JSON 字段字节不变；原企业投递/报告快照字节级签收（等企业任务交棒）。
