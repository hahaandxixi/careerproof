## 3. 三项检查的实际结论

| 检查 | 覆盖 | 结论 |
| --- | --- | --- |
| 1. 重试返回同一逻辑结果，不重复创建项目/版本 | `test_failed_upload_retry…`（HEAD 既有，:232-292） | **通过**：同 `versionId`/`taskId`；扫描调用恒为 1（`len(calls)==1`）；`versions` 长度 1；项目未被重建 |
| 2. 不同 owner 不能凭相同 requestId 获取他人结果 | `test_upload_request_key_is_scoped_to_owner_and_project`（:295-379，**他人未提交新增**，非我改动） | **通过**：Bob 对 Alice 项目同键 → 404；Bob 自己项目同键 → 得自己的版本/任务；Alice 侧仍只有自己的版本 |
| 3. 同 requestId 不同内容/目标项目遵循既有契约 | 同上两条 | **通过**：换内容 → 409；换 `materialRole` → 409；**换目标项目** → 建该项目的独立版本（202，versionId 不同），不绑定原项目材料 |

第 3 项的“换目标项目”契约值得单列：`version_by_request` 按 `(project_id, request_id)` 查，
所以同键用于另一项目**不会**返回原项目结果，而是新建——这正是 `uq_project_upload_request`
的既有语义，测试以 202 + 不同 versionId 显式断言，非静默绑定。

## 6. 未验证范围（不要据此扩大结论）

1. **只验证了顺序重试，不是并发幂等。** 客户端超时重试是"先提交成功、再重放"，本轮覆盖的正是该序列；
   两个请求**同时**到达的竞态（SQLite 下无法代表 PG 行锁）**未验证**。`create_project_version`
   依赖 `owned_project(..., lock=True)` 在 PostgreSQL 上序列化，SQLite 测试不证明该行锁行为
   （夹具 docstring 亦注明）。
2. **未在 PostgreSQL 上验证** `uq_project_upload_request` 的真实唯一性仲裁与 `FOR UPDATE` 语义。
3. 未验证"首次请求已提交、客户端超时、且重试时传入**不同文件名但相同字节**"的情形——
   幂等键比对的是 `content_hash` 与 `material_role`，文件名不在比对范围（代码可读出的既有契约，
   本轮未构造用例）。
4. 67 的前端 lib 层（mock client）与页面级竞态未在本轮重跑；本轮只覆盖后端持久化面。
