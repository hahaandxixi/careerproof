## 2. 资源清理：发现并修正了一个**假测试**

上轮的 `path.unlink()` 断言是无效的：CPython 引用计数会在函数返回时关闭句柄，所以即使解析器
完全不 close，`unlink()` 依然成功。本轮实测：

| 源码 | encrypted 用例的 `Document.close` 调用数 |
| --- | --- |
| 正常（`with fitz.open`） | **2** |
| 突变（去掉 `with`，故意泄漏） | **1**（仅 GC 终结器） |

因此改为**开/关计数相等**断言（`_open_calls == _close_calls`）。突变验证：

```text
正常:   15 passed
突变:   1 failed — AssertionError: opened 2 document(s) but closed 1
恢复:   26 passed（含 test_document_ocr.py）, ruff All checks passed
```

**如实声明局限**：PyMuPDF 在 GC 时也会 close，所以该断言能抓"开了从不释放"，
**不能**区分"显式 with 关闭"与"终结器关闭"。这一条已写进测试 docstring，不夸大为"显式释放已验证"。

另按失败形态分两类断言：
- 打开后失败（加密 PDF）：文件可删除 + 关闭数==打开数；
- 从未打开（损坏 PDF/DOCX）：`close` 计数必须为 **0**，不得凭空关闭。

## 2b. 第三轮：用替身彻底摆脱 GC 兜底（已完成）

上面的计数断言仍受 GC 影响，不足以证明「释放是显式发生的」。本轮改用**替身对象**：

- 新文件 `test_parser_release_double.py`（**3 passed**），对**未修改的** `parse_document` 注入替身；
- 替身 `RecordingDocument` 实现 `__enter__` / `__exit__` / `close` 并记录事件顺序，
  **不实现 `__del__`**、不接触真实文件，故释放不可能来自解释器或 OS；
- 测试持有强引用直到断言结束（`assert created == [document]`）；
- 覆盖两条路径：
  1. 正常读取 → 事件必须是 `["enter", "exit(none)"]`，且 `close` **未**被调用（释放走上下文协议）；
  2. 读取中抛出预期解析异常 → 事件必须是 `["enter", "exit(ValueError)"]`，异常被转换为
     `AppError(4024)`，且 `close` 仍未被调用（转换不得绕过上下文退出）。

**回归证明（不改坏共享工作区）**：`probe_release_test_double.py` 把 `document_parser.py`
复制到 `backend/.tmp/t71-copybreak/broken_parser.py` 并删除 `with` 上下文管理，
用同目录 `conftest.py` 在测试导入前替换 `sys.modules['app.tools.document_parser']`，
其余 `app.*` 仍来自真实后端。结果：

```text
替身测试（真实源码）: 3 passed
替身测试（损坏副本）: 2 failed, 1 passed
  AssertionError: []            <- 两个 exit 断言都看到空事件，证明没发生上下文退出
```

损坏副本仅用临时目录，**共享工作区 `document_parser.py` 哈希未变**
（`2b109489…01a72`），临时目录用后已删除。

**仍未做到的**：真实 PyMuPDF 文档对象在异常路径上的释放仍无法与"GC 兜底"区分——
本轮证明的是**生产解析函数的控制流**确实执行了上下文退出，不是 PyMuPDF 内部句柄的最终释放。
