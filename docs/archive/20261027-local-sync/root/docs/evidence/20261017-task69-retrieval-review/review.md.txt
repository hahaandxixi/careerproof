## 判定

Z61 的核心修复**成立**：过滤先于排序（`WITH owned_chunks AS MATERIALIZED` + 外层余弦排序），
`count(*) OVER ()` 在 CTE 内、外层 LIMIT 之前取值，故 `owned_matches` 是预截断的自有命中总数。
编译后的 PG 语句实测（`probe_version_dimension.raw.out` A 段）：

```sql
WITH owned_chunks AS MATERIALIZED (
  SELECT …, count(*) OVER () AS owned_matches
  FROM knowledge_chunks
  WHERE knowledge_chunks.source_id IN (__[POSTCOMPILE_source_id_1]))
SELECT … FROM owned_chunks ORDER BY owned_chunks.embedding <=> %(embedding_1)s LIMIT …
```

**发现 1 处可复现缺陷（1 项，已停止继续深挖）**

### V1 — 中：自有过滤缺少「版本」维度，被新版取代的简历/项目内容仍可被检索到

- 位置：`backend/app/services/retrieval.py:255-296`（`allowed_ids` 构造 + `WHERE source_id IN allowed_ids`）。
- 反例（独立 SQLite 拓扑，非复制 Z61 自证）：
  - 同一 `Resume` 下 v1、v2 各一个 `ResumeSection`；同一 `Project` 下 v1、v2 各一个 `ProjectFile`；
    均未归档。
  - 用 `retrieval.py:255-267` 的**原样谓词**求 `allowed_ids` → **4 条全部入选**；
    `probe_version_dimension.py` 的 B1/B2 均 FAIL：`superseded resume v1 section admitted: True`、
    `superseded project v1 file admitted: True`。
  - 即用户上传简历/项目 v2 后，`/knowledge/search` 仍可能返回 v1 旧段落与 v1 旧文件内容。
- 机制：`allowed_ids` 只按 `Resume.student_id` / `Project.student_id` 与 `is_archived` 过滤，
  **没有 `resume_version_id` / `project_version_id` 条件**；`delete_source_chunks` 只在
  *同一版本重解析* 时清理（`services/portfolio.py:432-437`、`524-529`），新版本上传不清理旧版本，
  `ResumeVersion`/`ProjectVersion` 也没有 `is_archived` 列可让旧版本退出。`KnowledgeChunk` 查询同样
  不带 `source_type` 判别式（A2 实测无），仅靠 UUID 全局唯一性兜底，不构成版本隔离。
- **真实可达路径（项目侧）**：`POST /api/v1/projects/{project_id}/versions`
  （`services/portfolio.py:369` `next_project_version` → 新建 `ProjectVersion` 与其 `ProjectFile`）。
  既有测试 `app/tests/test_real_matching.py:763-774` 即走该端点造出 v2；此后 v1 的 `ProjectFile`
  行仍在、`Project.is_archived` 仍为 False，于是 v1 与 v2 的文件**同时**进入 `allowed_ids`。
- 影响：检索结果混入已被取代的材料；属于任务卡所述「跨 owner / **版本**泄露」中的版本面。
- 非跨 owner：`allowed_ids` 严格来自本人 `student_id`，跨 owner 未发现泄露面。
