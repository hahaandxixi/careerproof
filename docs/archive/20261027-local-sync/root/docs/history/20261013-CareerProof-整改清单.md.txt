## 一、执行摘要

### 一句话判断

> **技术底子足够好，但有三件事在拖它：自动化门禁为零、界面数值与引擎能力脱节、硬性交付物三项为零。**

其中最反常的是：**第三件比前两件都重要，却一项都不需要写代码。** 项目在 27 天里产出 59 MB 验收证据、302 次提交、23k 行测试，却没有录一个视频、没有定许可证、没有给评委一条访问路径。

### 分维度评分

| 维度 | 评分 | 主要依据 |
|---|---|---|
| 工程严谨度 | **A** | 收据式 AI 计量、DB CAS 任务租约、`pg_blocking_pids` 验证真实行锁竞态、随机 schema 测试隔离、启动器防 PID 复用 ✅ |
| 边界设计 | **A−** | AI 无法改分（`final_score` 全仓唯一赋值点 `matcher.py:165`）✅、评级上限纯本地算 + 读时二次复核、第三方程式码永不提级、逐图同意、provider 端点白名单 |
| 诚实度 | **A** | `humanReview` 必须恰为 `false` 否则 runner raise、语义指标恒 null 并注明原因、自列 5 项未完成上线要求 |
| 前端 | **B** | 类型安全优秀（`any` 0 处、`strict: true`）✅、401 单飞刷新 + 竞态单测质量高；但 lint 不可运行、长列表无分页、`React.memo` 0 处 |
| 数据层 | **C+** | 全库无 jsonb / GIN / pg_trgm ✅、CHECK 只存在于 3 个模型文件 ✅、索引按单列建而查询按复合+排序用、账号注销路径被锁死 |
| API 契约 | **C** | 24 个端点返回裸 `dict`、三种分页风格并存、两处静默截断 100 条 |
| 产品表达 | **D** | 分数真实区间 0–65 却标「0—100」✅、证据等级实际 3 级却标「X/5」✅ |
| 交付就绪度 | **D** | 视频、LICENSE、评审访问、签署全部为零 |
| 可运维性 | **D** | 无 CI、无覆盖率阈值、启动链路 Windows-only、Dockerfile 不在 compose 里且不跑迁移、`DEBUG` 与 `APP_ENV` 脱钩 ✅ |

### P0-1.1 分数区间标注错误 ✅

| 项 | 内容 |
|---|---|
| **问题** | 界面标注「0—100分」，引擎实际上限 **65**，且单项分数只可能是 `{0, 10, 15, 30, 40, 65}` 六个值 |
| **证据** | `backend/app/tools/matcher.py:18` (`STRENGTH_SCORE` 最大 0.65)、`:165` (`final_score = rule_score * 100`)、`:171` (`overall_score` 上限 65)；`backend/app/tests/test_matcher.py:22` 断言 `overall_score == 65` |
| **前端位置** | `jianli/src/components/ApplicationBoard.tsx:116`（「数值为原报告0—100分」）、`:120`（`{item.finalScore} / 100`）、`jianli/src/lib/types.ts:89`（`// 0-100`） |
| **根因** | 前端测试夹具 `jianli/tests/application-list.test.mjs:64` 用了 `score: 80` —— **一个后端永远不可能产出的值**，所以这个错位从未被测试发现 |
| **影响** | 拿到最强证据的学生看到「65 / 100」，会认为自己只达到 65%，而 **65 就是公式上限**，实际已满分 |
| **修法 A（保守，推荐）** | 3 处文案/注释改为 `0–65`；同时把测试夹具改为真实可达值 |
| **修法 B（激进）** | `matcher.py:171` 改为按 0.65 归一化到 0–100。**注意：历史报告快照存的是 65，改归一化会让新旧报告口径不一致**，需同时处理快照兼容 |
| **验收** | `grep -rn "0—100\|\/ 100\|0-100" jianli/src` 无残留；前端测试不再使用不可达分数 |

## 三、批次 2：安全

### P0-2.1 生产 JWT 默认密钥可通过校验 ✅

| 项 | 内容 |
|---|---|
| **问题** | `config.py:22` 默认值 `"development-only-secret-change-before-production"`（48 字符）；`:77-83` 的校验器只在 `app_env == "production"` **且 `len(value) < 32`** 时拒绝 |
| **后果** | 48 字符的默认值**直接通过生产校验**。任何 `APP_ENV=production` 但忘记设 `JWT_SECRET` 的部署，等于用写在仓库里的公开密钥签发所有会话令牌 |
| **修法** | 生产环境显式拒绝该已知默认值（或拒绝任何出现在仓库中的值） |
| **验收** | 新增测试：`APP_ENV=production` + 默认密钥 → `Settings()` 抛错 |

### P0-2.2 `DEBUG` 与 `APP_ENV` 脱钩 ✅

| 项 | 内容 |
|---|---|
| **问题** | `config.py:19` `debug: bool = True`，**没有任何校验器把它与 `app_env` 绑定**（对比 `jwt_secret` 的校验器是绑了的）；`.env.example:3` 也把 `DEBUG=true` 作为示例值 |

### P1-2.6 Refresh Token 无重用检测

| 项 | 内容 |
|---|---|
| **问题** | `auth.py:64-75` 只把旧 token 标 `revoked_at` 并签发新的。**攻击者使用已撤销的 refresh 时，系统仅返回 401，不撤销该用户全部会话、不写审计** |
| **已做对的部分** | 轮换 ✅、JTI 只存 SHA256 哈希（DB 泄露不暴露可用令牌）✅ |
| **修法** | 检测到已撤销 refresh 被再次使用时，撤销该用户全部会话并写审计日志 |
| **验收** | 重放已撤销 refresh → 该用户所有会话失效 |

### P1-2.7 Access Token 不可撤销

| 项 | 内容 |

| **修法（长期）** | jti denylist（可用 Redis 或 `refresh_tokens` 同表） |
| **验收** | 要么实现 denylist，要么在文档中明确该窗口并接受 |

## 附录 C：一个元观察

三轮分析中，我**三次推翻委派分析给出的强结论**：

| 被推翻的结论 | 实际情况 |
|---|---|
| ⚠️「图片无脱敏出境」是 P0 疏漏 | 已在 `AI与数据边界.md:23` 明确披露 + `visual_evidence.py:172-175` 逐图强制同意 + 提示用户自行去敏。**是显式设计取舍，不是隐藏缺陷** |
| ⚠️「额度双轨」是并发绕过漏洞 | `analysis.py:304-346` 的 `_daily_ai_budget` **持用户行锁跨付费调用**（`with_for_update(key_share=True)`），并发无法通过同一快照；且文档自陈覆盖范围。**真问题是记账精度，不是并发** |
| ⚠️「FastAPI 断言校验提示词没写」 | rubric 通过 `evidence_workflow.py:114` 注入、`provider.py:329` 明确指令「按 rating_rubric 逐项判断」、`skill_rubric.py:15` 已写明该规则。**模型是被告知的**；真正的错配窄得多（片段窗口 vs 字面校验） |

**这个规律本身就是对项目的评价**：CareerProof 的自我文档化（`AI与数据边界.md`、各 README、代码内注释）**比一个外部读者的第一印象更准确**。在一个学生比赛项目里这是反常的。

它意味着：**攻击这个项目时最容易出错的地方，是低估它。** 它的真问题不在「藏了坏东西」，而在三件事——**记录太多但零自动化门禁、界面标签与引擎能力脱节、以及硬性交付物还是零**。

唯一的例外是 `backend/README.md:190` 那句关于通知中心的过期声称（见 P0-1.3），也是修复成本最低的一处。
